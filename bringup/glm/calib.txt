How a client talks to a node. The node's side is `node/src/wire.rs`, and this document
and that file's header say the same thing; if they ever disagree, the code is wrong.

One TCP connection carries one session at a time. Both directions are a stream of
little-endian unsigned 32-bit words. There is no framing beyond TCP's own: no length
fields, no delimiters, no escaping. A reader that started at the connection is always at a
word boundary, and control values live above the vocabulary, so no value ever needs to be
distinguished from data by anything but its size.
The stream in is the transcript the model sees. The stream out is the transcript it
produces. Nothing is transformed on either side, so a captured stream is a replay.
BOS, EOS and the vocabulary size are constants of the model, and the bundle's manifest
states them in its `[model]` table (`docs/bundle.md`) so a client reads them from the
same directory the node loads. GENERATE and SCORE are constants of the protocol.
After SCORE, every id the client feeds is answered, before it is fed, with one word
holding an f32: ln p of that id given everything before it, under the model's own
distribution (no temperature, no top-k, no top-p; the sampling recipe is for draws). The
word is the f32's bits, little-endian, in the same four bytes an id would take; a client
knows which it is reading because it sent SCORE. Ids fed before SCORE are context and are
not scored. Scoring persists for the sequence: a GENERATE after it still streams ids, and
ids fed after that are scored again. BOS ends it.
client → node   BOS, id, id, …, SCORE, id, id, id
node → client   f32, f32, f32                       (one per id after SCORE, as each is fed)
This is what likelihood-scored benchmarks and rerankers need: the prompt fed unscored,
then the candidate's ids scored and summed. A prompt shared by several candidates is
served from the node's store on the second and later connections, with only its last
position recomputed, so four choices cost four candidates and one prompt.

The identity is FNV-1a over the bytes of the bundle's `manifest.toml`, 64-bit, offset
basis `0xcbf29ce484222325`, prime `0x100000001b3`. The manifest names the checkpoint
revision, the recipe, the calibration text and the hash of every file, so equal
identities mean the client's tokenizer and the node's weights came from the same
checkpoint. A client sends `0` to accept any node. The node refuses a bad magic, a
different version, or a nonzero identity that is not its own, by closing the connection
without writing its header. Otherwise it writes its header and reads words.
client → node   BOS, id, id, id, …, GENERATE
node → client   id, id, id, …, EOS          (each word written the moment it is sampled)
client → node   id, id, …, GENERATE          (optional: continue the same sequence)
client → node   BOS, …                       (optional: a new sequence on the same connection)
Prompt ids are fed to the model as they arrive, in whatever steps arrive: ids already in
the socket's buffer go through the model together, up to 32 a step, and a trickle of
single ids goes one at a time. A position's result does not depend on how many stepped
with it (the node's own gate: every position's dumps byte-identical either way). On
GENERATE the node samples, writes the id, feeds it back, and repeats until it writes EOS
or the context is full. Every id that crosses the wire in either direction is in the
cache, so a continuation after EOS is exactly the transcript so far plus the new ids.
The node keeps the cache rows of every transcript it has computed, in host memory,
keyed by a running hash of the ids. As a prompt's ids arrive they are matched against
that store, and nothing is computed until the first id the node has not seen after that
prefix; the card is then seeded from the longest match and computing resumes there. A
client sees only that a repeated or extended transcript answers faster. The rows a hit
installs are the bytes a miss would have produced, so this is invisible to the stream.
The node does not read the socket while generating. Abort is closing the connection: the
node's next write fails, it stops, and it returns to accepting. There is no stop verb and
no token limit on the wire; the node runs to EOS or a full context (the header's
positions), and a full context closes the connection, since the sequence cannot continue.
A node serves one connection at a time, because it holds one attention cache. Nagle's
algorithm is off on the node's socket, so a four-byte token leaves when it is sampled
The stream is readable with nothing but netcat. The bytes below are the header with

The version in the header covers the word alphabet and the header layout. Anything added
later, a token limit, a seed override, a reference to a compiled grammar for structured
output, is a new verb, a new header field, or both, under a new version. A node speaks
exactly one version and refuses the others; the client decides what to do with that.

The one addition already sketched: structured output is a mask on the logits before the
draw. The grammar is compiled at the edge, where the tokenizer is, into an automaton over
token ids, and sent with the request or referenced by hash; the node holds a state, masks
by lookup, samples, and advances by the id it drew. It never sees a character.

A topic note, not the project's root documentation. It sets down how this project

versus 100,000 accelerators serving 62 trillion tokens a week) and land on the same
shape. Where they name something we do without naming, we take the name. Where they
have an instrument we lack, it is listed at the end with a note on when we get to it.
Their phrase is *dense feedback*, and "dense" does not mean more logs. It means every
- **local** — tied to a kernel, an input condition, a code path, a launch parameter,
  so it narrows the problem instead of describing it;
- **cheap and timely** — answerable by a kernel test or a microbenchmark, not a full
  deployment, so a wrong hypothesis costs minutes;
- **objectively verifiable** — decided by a reference implementation, a test, or a
  controlled experiment, never by a correlation in a log.

The correspondence is close enough that their three example cases each have a
counterpart in the story log. Their KDA context-parallel bug — `tl.dot` silently
computing FP32 inputs in TF32, an error that only showed after accumulation over long
context — is the class our equality rule exists to catch, and the per-position logits
diff would have shown it growing with position. Their GIL-across-DeepEP finding is a
timeline observation we currently cannot make. Their KDA decode kernel, redundant
per-tile normalization merged into one block with a warp reduction, is the same
transformation as the expert kernel's cell-per-lane rewrite.
**What the 100k attention kernel taught (2026-09-19).** Three rewrites in an afternoon,
each measured with the statistics channel before the next: absorbed queries for all
heads in LDS (52 KB) left one workgroup per CU and nothing to hide row-load latency;
heads in registers with every wave re-reading every row made the kernel L2-bound at
twelve reads of the cache per token; staging rows in LDS with lanes owning sixteen
consecutive floats was a 16-way bank conflict. The shape that works: rows staged once,
lanes owning strided dims, two heads a wave with an online softmax, and the per-token
work (absorbed queries) in its own launch rather than repeated per chunk or serialized
in one workgroup. The phase stamps, not the timeline, distinguished each of these.
**Four lessons the n-token kernels taught (2026-09-19).** A runtime token count in an
unrolled loop became every block executed under masks, twice the one-token time: the
width is a `const` and the kernel dispatches on it. Forty-three unrolled steps of a
10,944-wide row put 190 registers and scratch in a kernel that needs 23: a round is eight
steps at most. Lanes reading their eight activations eight floats apart hit the same
banks four lanes at a time, an 8-way conflict that cost the multi-token rows kernels 20×
their weight-streaming time: staged at a stride of ten. And the code object in host
memory, fine at 48 KB of small kernels, cost every launch 8–14 µs of instruction fetch
over the link once the kernels doubled and a token's weights had streamed through L2
between launches: it lives in VRAM. Each was found with `bench-step` (an op at a time
with a wait after each) and the timeline, not by reading the code.
**A lesson the sampler gate taught (2026-09-18).** A workgroup barrier written as
`asm!("s_barrier")` is not `convergent` to LLVM, and the compiler duplicated one into both
arms of a divergent branch, so a wave with lanes on both sides barriered twice and the
kernel read LDS slots before other waves had written them. The release build failed 28 of
442 rows; a build with a few extra stores at the end passed all of them, which is how it
was found. `common::gfx11::workgroup_sync` is now the LLVM intrinsic between two `asm!`
compiler barriers. The gate that caught it is the shape every op gate should have: the
realization against its twin on real inputs and on the inputs real data never produces.
Three anchors, each with one job, none reducible to another. This is the part that
took the longest to get straight and the part most worth keeping straight.

The oracle's bits are not canonical: its reduction orders differ from every order of
ours by the same 1e-6 that ours differ from each other. The weights were trained under

determinism measure, and determinism is a contract about reduction order, not an
accuracy property. Quality lives in the recipe and is measured teacher-forced.

We introduce GLM-5.3-Flash, the first natively multimodal model in the GLM-5 series. With 320B total parameters and just 18B active parameters, it outperforms GLM-5.2 across benchmarks and real-world workloads at one-tenth the price, while approaching Claude Opus 4.8 on coding and agentic benchmarks.
GLM-5.3-Flash starts from a newly trained base model, with its architecture and training recipe redesigned around capability and efficiency. For the first time in the GLM series, we introduce a hybrid architecture combining sparse and linear attention, sharply reducing long-context serving costs while preserving precise long-context capabilities. The model also adopts Manifold-Constrained Hyper-Connections (mHC) to further improve scaling efficiency. Together with our latest 30T-token multimodal pre-training corpus, these changes enable GLM-5.3-Flash to deliver more intelligence with less compute.
GLM-5.3-Flash supports deployment with the following frameworks. Feel free to try them out:
- GLM-5.3-Flash supports controlling the thinking budget through the `reasoning_effort` parameter, which accepts three levels: `low`, `high`, and `max`. It defaults to `max` if not passed (or if set to any other value). To use `low` or `high`, pass them explicitly. For benchmark and leaderboard reproduction, keep the default `max`.
- In the chat template for GLM-5.3-Flash, `clear_thinking` defaults to `false` if not passed. For chat scenarios, explicitly pass `clear_thinking=true`.
* **HLE w/ tools (full set)**: We use sampling parameters of `temperature=1.0` and `top_p=0.95` for evaluation, with a maximum generation length of `163,840` tokens. The evaluation is conducted with a maximum context length of `300,000` tokens, using a context management strategy. We use GPT-5.6-luna (medium) as the judge model.
* **NL2Repo**: We evaluated NL2Repo with temperature=1.0, top_p=1.0, and max_new_tokens=64k under 1M context. To prevent hacking, we use rule-based and a LLM-based judgement to prevent malicious behaviors (e.g., unauthorized pip or curl operations).
* **DeepSWE**: We run DeepSWE using the mini-swe-agent harness with `temperature=0.95`, `top_p=1.0`, `timeout=6h` and 400K context.
* **Terminal-Bench 2.1**: We evaluate in Claude Code 2.1.207 with temperature=1.0, top_p=1, max_new_tokens=65536 with 6h timeout.
* **Toolathlon Verified**: We obtain all results via the official evaluation service and report pass@1 averaged over 3 independent runs.
* **AutomationBench**: We evaluate on AutomationBench **v1.0.6**, incorporating the fix for the `null`-type handling issue introduced in PR #13.
* **GDPval-AA v2**: Models are evaluated by Artificial Analysis.
* **BabyVision**: We use temperature=1.0, top_p=0.95, and a maximum context length of 164K tokens. We resize the input images such that their shorter side is at least 1.5K pixels, consistent with other baselines.
